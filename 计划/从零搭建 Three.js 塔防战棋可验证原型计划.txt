从零搭建 Three.js 塔防战棋可验证原型计划
1. 项目目标
从空项目开始，搭建一套可以实际运行和反复测试的 Three.js 3D 战斗原型。

原型需要完成一张类似明日方舟基础关卡的斜视角战斗地图，但不直接复制明日方舟的全部规则。它首先用于验证以下内容：

3D地图、地面、高台、障碍物和基础光影是否能清楚表达。
Q版角色Sprite放置在3D地图中是否具有足够的空间感和可读性。
角色部署、攻击、技能和敌人推进是否能形成完整战斗。
角色可移动、自动转向和高频调位是否容易操作。
猎人加入后，救援、撤离、部署范围和移动是否会造成额外操作负担。
未来是否可以将占位Sprite替换为真实Spine模型，并继续使用同一套战斗逻辑。
未明确的规则是否能够通过原型暴露出问题，而不是停留在文字设计阶段。
本阶段不制作完整游戏，不制作完整肉鸽系统，不制作横板战斗。

最终结果应该是一个可以被用户打开、操作、截图、录屏并用于讨论规则的战斗切片。

2. 研究与认证流程
开发Agent需要按以下顺序进行研究，不应直接凭印象实现。

2.1 明日方舟规则研究
研究目标不是复刻明日方舟，而是建立一份“基础塔防战斗对照表”。

需要确认：

关卡进入后的战斗流程。
玩家如何部署角色。
部署费用或部署资源如何影响角色进入战场。
地面与高台的基础区别。
近战与远程角色的部署限制。
角色部署后的朝向。
普攻索敌与攻击范围。
敌人的行走路线。
角色阻挡敌人的规则。
敌人抵达目标点后的失败处理。
技能充能与主动释放。
暂停、倍速和战斗信息展示。
关卡胜利、失败和重试流程。
当前可作为基础对照的公开资料指出，明日方舟的核心玩法是部署角色阻止敌人到达基地，角色具有不同职业和攻防职责，并受到部署区域、攻击范围和地形位置影响。[^1][^2]

研究结果需要生成一份简短文档：

ArknightsBaseline.md
文档必须分为：

明日方舟原有规则。
本项目准备沿用的规则。
本项目准备改变的规则。
当前无法从参考资料确认的内容。
不要把网上攻略中的数值直接当作项目规则。

2.2 参考视频认证
用户提供参考视频文件夹后，Agent需要逐个查看并记录。

每个视频建立一份观察记录：

ReferenceVideo_001.md
ReferenceVideo_002.md
记录：

视频名称。
观察时间段。
镜头角度。
地图透视方式。
地格是否清晰可见。
角色与地面的相对比例。
敌人出现方式。
角色移动和攻击反馈。
技能释放反馈。
UI布局。
暂停、倍速和操作方式。
与当前规则文档一致的内容。
与当前规则文档冲突的内容。
无法从视频判断的内容。
视频只用于确认视觉和操作感受，不把视频中没有明确展示的行为当作既定规则。

输出一份：

ReferenceValidation.md
其中每条结论标记为：

已确认。
高概率推断。
无法确认。
与当前设计冲突。
2.3 素材地址校对
用户提供素材文件夹或地址后，Agent需要先建立资产清单，再接入。

不能一边开发一边猜文件名。

输出：

AssetManifest.md
每个资产记录：

字段	内容
assetId	项目内部唯一ID
原文件名	素材原始名称
文件路径	实际路径或URL
类型	Sprite、Spine、模型、纹理、音频等

导出版本	Spine或其他工具版本
动画列表	已确认的动画名称
尺寸与比例	图片或模型尺寸
透明通道	有／无
许可状态	已确认／待确认
接入状态	未接入／占位／已接入

素材地址如果需要登录、跨域或临时令牌，先复制到项目可访问的本地资源目录，或实现一个明确的开发环境代理。不要把私人资源地址硬编码到正式代码。

3. 技术路线
3.1 默认技术栈
如果没有现有项目，默认创建：

Vite。
TypeScript。
Three.js。
原生DOM/CSS UI。
spine-ts或与实际导出版本匹配的官方Three.js运行时。
Vitest或项目已有测试工具。
Playwright用于浏览器验证和截图。
Three.js负责：

3D场景。
相机。
地图几何。
Sprite或Spine角色的空间定位。
灯光与阴影。
鼠标拾取。
战斗特效。
路线和范围可视化。
DOM/CSS负责：

顶部战斗信息。
角色列表。
技能按钮。
卡牌区域。
角色状态面板。
调试面板。
操作提示。
不要把所有UI绘制到Three.js Canvas里。战斗地图和UI需要分别维护，便于之后替换视觉设计。

Three.js官方示例和文档中的GLTF加载、控制器、阴影等能力可以作为3D场景的技术参考。[^4][^5]

3.2 渲染方式
原型使用：

WebGLRenderer。
正交相机或低视角透视相机。
OrbitControls只在开发模式启用。
正式战斗视角默认固定。
Raycaster处理地图和角色拾取。
DirectionalLight作为主光源。
AmbientLight或低强度半球光作为基础补光。
PCFSoftShadowMap或性能允许时的VSM阴影。
可选的环境雾和轻量后处理。
避免一开始使用复杂的WebGPU专属效果。当前目标是验证玩法和可读性，WebGL fallback更稳定。

4. 第一阶段：空项目与最小渲染闭环
4.1 创建项目
完成：

项目启动。
TypeScript编译。
Three.js渲染。
浏览器窗口自适应。
开发模式错误显示。
资源加载错误显示。
基础FPS或帧时间显示。
验收：

npm install成功。
npm run dev成功。
浏览器能看到Three.js场景。
npm run build成功。
页面失焦后不会产生异常时间跳跃。
4.2 创建基础场景
场景包含：

世界坐标轴。
斜视角相机。
地面平面。
主方向光。
补光。
阴影接收平面。
简单雾效。
可隐藏的开发网格。
相机默认显示一张完整的小地图，用户可以缩放，但默认不允许自由旋转，避免战斗坐标方向发生混乱。

4.3 创建3D地图网格
地图以逻辑方格定义：

type TileType = "ground" | "high" | "obstacle" | "deploy" | "spawn" | "goal";

type TileDefinition = {
  x: number;
  y: number;
  layer: number;
  type: TileType;
  walkable: boolean;
  deployable: boolean;
  blocksSight: boolean;
};
地图需要支持：

地面。
高台。
障碍。
敌人出生点。
水晶或目标点。
撤离点。
可部署区域。
猎人动态部署范围。
地图几何使用不同高度的方块或平台表现。逻辑格和显示格必须一一对应。

5. 第二阶段：Sprite角色与Three.js空间表现
5.1 第一版角色占位
在真实素材接入前，使用Q版占位Sprite：

每个角色使用不同颜色和轮廓。
Sprite始终面向相机或采用固定斜视角朝向。
角色脚底有阴影或椭圆投影。
角色脚底绑定逻辑地格。
角色头顶显示HP条、状态图标和选中框。
不使用简单圆球代替角色，避免无法验证Q版角色在地图中的比例和可读性。
建议至少准备：

猎人。
菲奥蕾。
近距离攻击角色。
远距离攻击角色。
普通近战敌人。
普通远程敌人。
5.2 Sprite空间规则
每个角色有：

type VisualAnchor = {
  worldPosition: Vector3;
  footOffset: number;
  sortingLayer: number;
  billboardMode: "camera" | "fixed";
};
要求：

移动时脚底位置沿逻辑路径移动。
角色模型不以中心点作为格子归属点。
高台与地面使用不同的世界高度。
角色攻击特效从角色身体或武器锚点发出。
受击闪白、死亡淡出、濒死倒地和选中反馈可独立控制。
5.3 Spine接入准备
真实Spine接入前先确认：

Spine编辑器版本。
JSON或二进制导出格式。
atlas文件。
png纹理。
premultiplied alpha设置。
skeleton数据版本。
是否使用裁剪、网格、IK、事件、皮肤或约束。
动画名称命名规则。
角色默认朝向。
是否需要左右翻转。
是否提供攻击事件帧。
spine-ts提供Core、WebGL和Three.js相关运行时模块，可作为候选方案；但具体接入必须匹配模型导出版本，不能混用不兼容版本。[^3]

创建统一接口：

interface CharacterVisual {
  load(): Promise<void>;
  setAnimation(name: string, loop: boolean): void;
  queueAnimation(name: string, loop: boolean): void;
  setFacing(direction: Direction): void;
  setVisible(value: boolean): void;
  setTint(color: number | null): void;
  update(deltaSeconds: number): void;
  dispose(): void;
}
占位Sprite和Spine角色都实现该接口。

这样战斗逻辑只调用：

visual.setAnimation("attack", false);
不直接依赖Sprite或Spine类型。

6. 第三阶段：类明日方舟基础关卡
本阶段先实现一个最小的传统斜视角防守关卡。

6.1 关卡布局
制作一张测试地图：

12～18列。
6～8行。
2条主要敌人路线。
少量障碍。
2个高台区域。
1个玩家目标点或水晶。
2个敌人出生点。
1个玩家初始部署区域。
1个撤离点。
1个猎人初始位置。
地图不要过大。原型需要让用户能够同时观察所有角色和敌人。

6.2 基础战斗流程
完整流程：

进入关卡。
显示敌人出生点、目标点和可部署区域。
角色始动量条开始积累。
玩家部署角色。
敌人从出生点沿路线推进。
角色自动索敌和攻击。
玩家可以移动角色。
玩家可以改变默认方向。
玩家可以释放技能。
敌人抵达目标点造成失败进度。
清除所有敌人后关卡胜利。
显示战斗结果和操作统计。
第一版只做一个胜利条件：清除指定波次并保护水晶。

7.1 角色基础字段

7.3 基础敌人
至少实现：

普通近战敌人。
普通远程敌人。
高生命值慢速敌人。
可被移动阻挡的敌人。
敌人必须拥有清楚的：

出现反馈。
移动路线。
目标锁定。
攻击预警。
受击反馈。
死亡反馈。
到达目标点反馈。
7.4 阻挡规则
第一版按类明日方舟基础规则实现：

己方角色可以阻挡敌人。
己方角色之间不互相阻挡。
敌人被阻挡后停止沿路线前进。
阻挡数量由角色属性决定。
超出阻挡数量的敌人继续寻找路径。
远程敌人可以在不接触时攻击合法目标。
濒死角色不再阻挡。
撤离中的角色不再阻挡。
你的移动系统允许角色主动调位，因此需要明确区分：

角色可以移动。
角色是否占据格子。
角色是否形成战斗阻挡。
角色是否可以穿过敌人。
原型默认：

角色不能穿过敌人。
角色可以穿过友方角色。
角色不能在友方占据的格子结束移动。
角色移动被敌人阻挡时，停止移动并恢复合法普攻。
8. 第五阶段：移动、方向和自动索敌
8.1 移动
实现：

点击角色。
点击目标格。
拖动角色到目标格。
A*寻路。
路径预览。
移动冷却。
被敌人阻挡后暂停。
玩家主动改道。
移动中不执行普通攻击。
释放技能取消移动。
取消操作不扣移动冷却。
地图高台与地面在移动逻辑上视为可直接通行。跨越高低台时：

路径线继续显示。
角色使用0.5～1秒淡出淡入。
状态继续计算。
切换完成前仍归属源地格。
角色不因为淡出获得无敌。
被击杀时仍按当前规则处理。
8.2 默认方向和临时朝向
保存两个方向：

默认方向：玩家指定，自动转向不会覆盖
当前方向：当前攻击使用
自动索敌：

先检查默认方向范围。
如果没有合法目标，检查其余三个方向。
使用攻击策略决定目标。
没有策略时，选择绝对距离最近的合法目标。
同距离时使用固定种子随机。
当前攻击未完成时不切换目标。
没有目标时回到默认方向。
8.3 攻击范围
范围判定必须同时服务：

普攻。
技能。
目标选择。
范围预览。
自动索敌。
伤害结算。
不要分别写五套近似逻辑。

范围判定考虑：

平面范围模板。
当前朝向。
地面或高台。
同层或异层。
远程标签。
高台遮挡。
目标可见性。
阵营。
目标当前生命周期。
当前原型默认实现：

非远程攻击只能命中同层逻辑格。
地面远程可以攻击范围内高台敌人。
地面远程不能穿过高台攻击高台后方的地面敌人。
高台远程可攻击横向范围内的不同高度目标。
高台遮挡采用格线检查。
飞行敌人使用独立高度层和可见性标记。
9. 第六阶段：猎人和救援机制
猎人不是普通部署角色。

9.1 猎人功能
猎人：

进入关卡时自动出现。
不占普通角色部署槽。
具有基本移动能力。
决定基础部署范围。
拥有影庭范围。
可以救援濒死角色。
可以回收存活角色。
不能进入自己的影庭。
死亡后延迟重生。
重生后回到菲奥蕾附近或起始点。
9.2 救援交互
流程：

点击濒死角色。
显示救援按钮。
点击后显示猎人路径。
显示预计抵达时间。
玩家确认。
猎人自动沿路径移动。
到达影庭有效范围后完成救援。
角色从濒死变为本场禁用、下一节点HP为1的状态。
猎人需要能够被玩家中途重新指挥。

如果路径受敌人阻挡：

猎人停止。
显示阻挡原因。
玩家可重新指定路径。
不自动选择高风险绕路，除非未来配置开启。
9.3 撤离交互
正常角色撤离方式：

进入猎人的影庭。
移动到地图撤离点。
第一版建议统一通过目标角色的撤离按钮完成：

选中角色
→ 点击撤离
→ 如果目标是猎人影庭，自动前往猎人当前影庭
→ 如果目标是撤离点，自动前往撤离点
→ 到达后角色离场
撤离状态：

不受敌方普通攻击。
不可使用道具。
不接受普通目标型卡牌。
生命、Buff、Debuff和持续效果冻结。
技能冷却按原型配置继续计算。
再部署量条开始积累。
10. 第七阶段：濒死、死亡和状态继承
10.1 濒死
每场战斗第一次HP归零：

进入濒死。
显示倒地模型或替代Sprite。
显示独立救援倒计时。
不再阻挡敌人。
不再成为普通攻击目标。

21. 执行原则
先让一场基础战斗完整跑通，再扩展系统。
先用占位Sprite验证空间和交互，再接入Spine。
逻辑数据与Three.js表现分离。
规则冲突必须记录，不要静默覆盖。
未提供的素材不伪造为正式素材。
不把静态UI按钮当作功能完成。
不把自动播放动画当作真实战斗事件。
预览、索敌和结算必须共用判定逻辑。
所有临时数值进入配置。
每个阶段都保持可以启动、可以测试、可以回退。
优先解决操作负担、空间可读性和战斗状态正确性。
横板模式、肉鸽副本、完整养成和剧情系统放在基础战斗切片验证之后。
