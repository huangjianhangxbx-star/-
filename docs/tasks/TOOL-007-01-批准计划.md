# TOOL-007-01：编辑操作基础设施详细实施计划 v0.1

## 任务定位

本任务**不是新增 Minecraft 创造模式**，也不是做 Clipboard、印章或世界生成。

它只解决一个底层问题：

> 后续所有“修改体素”的工具，都必须共享一套可靠的
> **生成候选 → 预览 → 校验 → 执行 → 撤销/取消**
> 基础设施。

完成 007-01 以后，现有工坊的功能和操作习惯原则上应保持不变。

下一任务 `TOOL-007-02` 才开始真正实现 Minecraft 式创造建造模式。

---

## 一、当前源码基线与问题

当前已有基础很好，不允许推倒重做。

现状包括：

- `core/brush.ts` 已有 `brushCandidates()`，能生成 `applied / noop / skipped` 候选；
- `applyBrush()` 已经支持 seen 去重、预算检查和批量修改；
- `EditorDocument` 已有 `begin / commit / cancel / undo / redo / batch`；
- 连续笔画已经是一笔一次撤销；
- Rectangle 已经支持分批执行和 Esc 取消；
- WorkshopSession 已保证**未提交笔画不能污染 AssetDocument**；
- RebuildQueue 已处理旧网格结果不能覆盖新状态。

因此本任务不是再造 transaction/history。

真正需要解决的是：

**现在“操作生命周期”仍然大量散落在 `desktop/renderer.ts`。**

例如当前：

```text
preview()
    ↓
brushCandidates(...)

apply()
    ↓
brushCandidates(...)   ← 又算一遍
    ↓
applyBrush(...)
```

矩形也存在：

```text
pointermove
→ 自己建立 candidates 作为预览

pointerup
→ 再遍历整个矩形重新执行
```

同时：

```text
drawing
start
last
strokeConfig
strokeSeen
batch
batchToken
Esc
blur
pointercancel
```

这些生命周期状态都直接堆在 renderer。

这对现在几个工具还能工作，但继续加入：

- 创造模式；
- Selection；
- Clipboard；
- Stamp；
- 世界生成；

以后会越来越容易各写一套自己的取消、预算、历史和预览逻辑。

# 二、本任务最终目标

形成一个统一概念：

```text
输入/鼠标命中
      ↓
【Build Plan】
      ↓
EditOperationPlan
      │
      ├─ Candidates
      ├─ Applied
      ├─ No-op
      ├─ Skipped
      ├─ Estimated Change
      └─ Dirty Area
      ↓
【Preview】
      ↓
用户确认 / 持续拖动
      ↓
【Apply SAME Plan】
      ↓
EditorDocument Transaction
      ↓
Commit / Cancel
```

最重要的一条：

# **预览和实际执行不能各自独立计算“我要改哪些格”。**

一个 Plan 描述什么，最终就执行什么。

# 三、推荐新增的核心结构

文件名允许 Codex 根据现有结构小幅调整，但推荐新增：

```text
core/edit-operation.ts
```

不要一开始搞成庞大的 Command Framework。

首版只需要足够支撑现有 Brush / Rectangle，并为 007-02、03 留接口。

建议核心类型类似：

```ts
type EditOperationPlan = {
  kind: string;

  candidates: Candidate[];

  summary: {
    applied: number;
    noop: number;
    skipped: number;
    estimatedAdds: number;
    estimatedRemoves: number;
  };
};
```

以及一个操作会话：

```text
EditOperationSession
```

概念职责：

```text
begin()
plan()
apply(plan)
commit()
cancel()
```

内部持有：

```text
seen
active
cancelToken / generation
```

但：

> **EditorDocument 仍然是唯一真正拥有历史和事务的数据层。**

不要再建立第二套 undo stack。

`EditOperationSession` 只是协调：

> 一个用户动作什么时候开始、执行、结束。

# 四、Task 01A：把 Candidate 升级成正式 Plan

以现有 `brushCandidates()` 为基础，不重新发明算法。

当前：

```text
brushCandidates()
→ Candidate[]
```

建议演化为：

```text
buildBrushPlan(...)
→ EditOperationPlan
```

内部仍可继续调用 `brushCandidates()`。

Plan 至少应该预先知道：

- 哪些格会实际改变；
- 哪些是 noop；
- 哪些因为 protected / missing-support 等原因跳过；
- 最多新增多少体素；
- 操作是否超过预算。

### 预算检查尽量提前到 Plan 阶段

例如：

> 一个 25 万以上的矩形

最好在任何格子实际发生修改以前就被拒绝。

而不是：

> 修改了一部分 → 超预算 → 再依靠 cancel 回滚。

后者虽然现在数据上安全，但不利于后面大型操作。

---

# 五、Task 01B：Preview 与 Apply 使用同一 Plan

当前 Brush preview 会计算一次 Candidate，执行时又重新计算。

改为：

```text
hit
 ↓
buildPlan()
 ↓
currentPreviewPlan
 ├─ View.brushPreview(plan.candidates)
 └─ applyPlan(plan)
```

### 普通单点

Pointer Down：

```text
建立 Plan
→ 显示
→ Apply 同一个 Plan
```

### 连续笔画

每个采样位置：

```text
Sample Hit
→ Plan
→ Apply Plan
```

整个 Stroke 共享：

```text
seen
transaction
config snapshot
```

仍然：

> 一次按下 → 拖动 → 松开 = 一次 Undo。

# 六、Task 01C：配置冻结

现有 `strokeConfig` 思路是正确的，要正式化。

一次笔画开始后：

```text
颜色
笔刷尺寸
shape
thickness
working layer
direction
mode
action
```

全部冻结。

即便用户因为某种 UI/快捷键改变了外部控件：

> 当前笔画也不能半途改变含义。

直到下一笔才读取新配置。

为后面的 Minecraft 模式同样保留这种原则。

# 七、Task 01D：Rectangle 也改成 Plan

当前 Rectangle preview 和 pointerup 执行逻辑是两套循环。

改为：

```text
Rectangle Start
+
Rectangle End
+
Frozen Config
       ↓
buildRectanglePlan()
```

同一个 Plan：

```text
Preview
↓
Pointer Up
↓
Execute
```

如果鼠标位置确实发生变化：

> 创建新的 Plan 替代旧 Preview。

但相同 Start / End / Config 下：

> PointerUp 不得再另外构造一套不同 Candidate。

# 八、Task 01E：统一操作生命周期

把 renderer 里的这些散落状态：

```text
drawing
strokeConfig
strokeSeen
batchToken
batch
```

尽量收束到一个明确的 Operation Session / Controller。

Renderer 继续负责：

- Pointer Events；
- UI；
- View；
- Message。

但不应该继续负责决定：

> “什么时候这个事务才算一个事务。”

理想关系：

```text
renderer.ts
    ↓ input

EditOperationSession
    ↓

EditorDocument
```

而不是：

```text
renderer.ts
├─ begin
├─ commit
├─ cancel
├─ seen
├─ budget
├─ batch token
├─ partial state
└─ ...
```

# 九、Task 01F：统一取消路径

现在已经有：

- Esc；
- pointercancel；
- window blur；
- error；
- batchToken。

这些行为必须保留。

但重构后统一走：

```text
operation.cancel()
```

然后由一个地方保证：

```text
EditorDocument.cancel()
清空 preview
清空 seen
取消异步 batch
invalidate rebuild
恢复真实数据
```

避免未来创造模式出现：

> Esc 能取消 Brush，却取消不了 Stamp。

# 十九、验收标准

TOOL-007-01 可以标记完成，当且仅当：

- 现有笔刷 Preview 和 Apply 已共享同一操作计划；
- Rectangle Preview / Commit 使用同一计划逻辑；
- 连续 Stroke 共用一个 Transaction；
- 配置在一笔内被冻结；
- seen / cancel / batch 生命周期从 Renderer 收束；
- 大 Rectangle 能分片并取消；
- No-op 不产生历史；
- Skipped 不杀死整笔；
- Budget 在修改前可预检；
- 任何异常可完整 rollback；
- WorkshopSession 不会同步未 Commit 的编辑；
- 原 Workshop-M2.0 功能全部回归；
- TOOL-006 暗色/快捷键/公共库 UX 不退化。
