# 0. 本阶段为什么必须先做

当前独立暗牢已经具备：

- 独立探索入口；
- Unity 中型暗牢派生地图；
- 入口 / 出口；
- 三处篝火；
- 站岗 / 巡逻敌人；
- 敌人感知提示；
- 第一击入战；
- 跟随 / 队友自治；
- 架势 / 虚血；
- 独立出口胜利；
- HUD 抽屉等探索界面调整。

但目前还无法判断探索战斗是否“好玩”，因为最基础的战斗样本仍然失真：

1. 己方原始 roster 过多，局部遭遇容易形成多人围攻；
2. 当前独立暗牢每个房间最多只尝试放 2 名敌人；
3. 普通探索敌人约 85 HP、Heavy 135 HP，消失过快；
4. 探索玩家基础移动仍为 1.70，探索敌人仍约 1.275，中型地图里明显拖沓；
5. 后续 EC-02～EC-16 的切人、闪避、Break 2.0、三技能、敌人能力升级都必须建立在一个可信的“双人战斗环境”上才能判断价值。

所以 EC-01 的任务不是“让最终战斗系统完成”。

它只负责建立：

> **猎人 + 1位伙伴，面对更密集、更耐打、移动更快的探索遭遇。**

然后立刻交给用户试玩。

# 1. 用户已经明确确认的目标

本阶段视为明确要求：

1. 独立探索副本暂时限制为 **2名本体**：
   - 猎人固定；
   - 出发前任选 1 名伙伴。
2. 探索模式敌我双方移动速度都要提高。
3. 探索敌人的生命值暂时 **加倍**。
4. 当前单次遭遇敌人数太少，需要提高局部遭遇密度。
5. 塔防正在收缩为兼容玩法；本阶段探索参数不再要求与塔防完全一致。

以下数值和具体实现结构属于本计划的原型建议，需要通过试玩验证，不代表最终平衡。

本阶段只做六件事：

**以下全部留给后续 EC，不提前做：**

- 双角色快捷切换；
- Companion AI 2.0；
- 取消探索战斗锚点；
- 全角色闪避；
- 走A重构；
- Telegraph；
- Break 2.0 / 强制位移 / 撞墙；
- 方向 / 背击 / 弱点；
- 三技能槽；
- 技能独立充能；
- 敌人新主动技能；
- 敌人闪避 / 格挡 / 反击；

- 角色完整重制。

这样用户试玩 EC-01 时，能够明确判断：

> “只是双人化 + 速度 + 耐久 + 敌群密度改变以后，战斗底盘感觉怎样？”

# 3. 双人出发模型

## 3.1 队伍组成

独立暗牢固定：

```text
Hunter
+
One Companion
```

猎人永远占一个位置，不可取消。

第二位置从当前可用本体中选择一位：

- 菲奥蕾；
- 伊内丝；
- 阿尔。

如果以后正式游戏只保留一位核心伙伴：

> 这套数据结构仍然成立，只需让第二位置自动锁定，不需要重做探索战斗。

---

## 3.2 出发前选择

在现有“出发账册 / 模式选择”里：

当玩家选择：

> `暗牢探索`

在携入确认之前出现一个轻量的：

### 同行伙伴

```text
猎人   [固定]

菲奥蕾
伊内丝
阿尔
```

一次只能选一个。

### 建议行为

- 默认不偷偷替玩家选；
- 玩家必须明确选择一位伙伴后才能确认进入暗牢；
- 选择可以在正式携入前反复修改；
- 不为此制作大型角色选择界面，只使用当前 UI 风格的小型角色卡 / 按钮；
- 塔防远征入口不显示此限制。

---

## 3.3 状态字段

建议在 `GameState` 使用清晰字段，例如：

```ts
explorationCompanionId?: string
```

或：

```ts
explorationParty?: [string, string]
```

首版更推荐：

```ts
explorationCompanionId
```

因为猎人是固定常量。

不要把这个选择偷塞进：

- `selectedBodyId`
- `partySelection`
- UI local state

它是一次探索出发的正式游戏状态。

---

## 3.4 核心查询

建立一个统一查询，例如：

```text
isStandaloneExplorationPartyMember(s, u)
```

或者：

```text
standalonePartyIds(s)
```

所有独立探索的“谁是本次队伍成员”都通过这一入口判断。

不要在：

- campfire
- exit
- party follow
- UI
- roster
- H/B
- enemy target query

里分别散写：

```text
u.id === 'hunter' || u.id === s.explorationCompanionId
```

避免后续 EC-02 / EC-09 改控制时到处找条件。

# 4. 进入暗牢时如何处理 roster

## 4.1 猎人

- `active`
- 出生于 Entry；
- 保留当前独立探索已有初始化规则。

## 4.2 被选伙伴

- `active`
- 与猎人一起进入副本；
- 出生在 Entry 附近最近合法位置；
- 立即进入当前已有探索软跟随逻辑。

不要两人完全堆在同一视觉坐标。

建议：

1. 以 Entry 为中心；
2. 使用当前 `canStop / navigation / surface`；
3. 查找约 0.6～1.0 U 的合法邻近点；
4. 优先放在猎人后侧/侧后；
5. 找不到时才允许复用 Entry 作为最后兜底。

---

## 4.3 未被选伙伴

未选角色必须：

- 不 active；
- 不进入探索跟随；
- 不参与共享视野；
- 不被敌人索敌；
- 不参与出口资格；
- 不接受篝火恢复；
- 不参与 H/B；
- 不参与局部AI；
- 不能被战斗中重新部署进入暗牢。

本阶段不要删除这些角色的数据。

它们仍然存在于 roster/profile，方便后续更换伙伴和未来删减角色时处理。

# 5. 战斗中的 roster UI

为了降低理解负担，独立暗牢战斗时：

> **同行者栏只显示本次真正出场的两名本体：猎人 + 伙伴。**

不要继续把未出场的两个人以“待部署”形式放在底栏，避免玩家误以为可以在副本中追加第三人。

出发前的伙伴选择界面仍可看到全部当前候选。

塔防 UI 不改。

# 6. 复制体在 EC-01 的处理

这一条是为了忠实实现“己方限制两人”。

## 推荐边界

在**独立暗牢探索**里：

> 暂时禁止新召唤复制体。

原因：

如果本体固定两人，但仍能召出多个复制体：

> 实际战斗人数仍然会迅速膨胀，EC-01 就无法验证真正的双人战斗压力。

### 注意

这不是删除复制体系统。

- 塔防继续可以使用；
- 旧探索支路沿当前规则；
- 复制体源码和构筑不删除；
- 后续 EC 阶段可以重新讨论“影体是否作为技能/资源重新进入主探索”。

独立暗牢中点击召影时：

> 核心规则明确拒绝，并给出原型说明。

例如：

```text
“双人探索验证中暂不可召影”
```

如果用户后续明确决定：

> 影体不计入两人限制

再单独恢复。

# 8. 探索移动速度独立

## 8.1 不再改 `baseMoveSpeed`

当前：

```text
baseMoveSpeed = 1.70
enemyTowerSpeed = 1.275
enemyExploreSpeed = 1.275
```

不要再通过：

```text
baseMoveSpeed = 2.4
```

提高探索速度。

否则塔防也被迫一起变。

---

## 8.2 新增探索己方速度参数

建议新增独立参数，例如：

```text
allyExploreSpeed = 2.40
enemyExploreSpeed = 1.90
```

第一轮测试值：

### 玩家 / 伙伴
`2.40`

相对当前 1.70 约提高 41%。

### 敌人
`1.90`

相对当前 1.275 约提高 49%。

这两个值不是最终平衡。

选择 2.40 / 1.90 的原因：

- 能明显感觉到中型地图节奏变化；
- 但没有直接把所有角色再次 ×2；
- 给后续 EC-03 的闪避、走A留出继续提升动作感的空间。

---

# 9. 速度必须通过统一 movementSpeed 生效

不能只改某个：

```text
u.speed
```

然后：

- WASD 是一种速度；
- AI 是另一种；
- 跟随又是一种。

要求：

### 独立探索本体
基础来源使用 `allyExploreSpeed`。

### 独立探索敌人
使用 `enemyExploreSpeed`。

之后仍叠加已有合法修正：

- 负重；
- slow；
- 破势移动锁；
- 跟随 catchup；
- 其他状态。

塔防仍：

- 玩家 1.70；
- 敌人 1.275；
- 不受本轮探索参数影响。

---

# 10. 跟随追队倍率

当前 `followCatchup = 1.15`。

EC-01 暂时不改。

因为提高探索基础速度以后：

```text
2.40 × 1.15 = 2.76
```

已经足够让伙伴重新追上猎人。

如果实际试玩出现：

- 伙伴频繁掉队；
- 转角后赶不上；

再在 EC-01 试玩修正里调整。

不要这次同时改太多速度维度。

# 11. 移动动画适配

提高世界移动速度以后要检查：

> 跑步动画是否明显“滑冰”。

如果当前 Spine 跑步播放速率支持安全倍率：

- 只对 `run` 动画按实际移动速度做轻量同步；
- 给播放速率设合理上下限；
- 不改变 attack / skill / hit / death 动画速率。

如果现有 Spine 层不适合在本轮安全调整：

> 只记录滑步问题，不为了动画重构阻塞 EC-01。

功能速度优先于最终美术。

# 12. 探索敌人 HP ×2

当前暗牢生成大致：

```text
普通 / 远程：
85 HP

Heavy：
135 HP
```

EC-01 第一轮：

```text
普通 / 远程：
170 HP

Heavy：
270 HP
```

建议不要直接在 `standalone-exploration.ts` 到处手写双倍数字。

可以建立：

```text
standaloneEnemyHpScale = 2.0
```

或者探索 balance 配置。

这样试玩后：

> 2.0 → 1.7

只需改参数。

---

# 13. 本阶段不同时提高敌人伤害

保持：

```text
damage ≈ 当前值
```

原因：

本轮已经同时发生：

- 己方从多人 → 2人；
- 敌群局部变多；
- 敌人HP ×2；
- 敌人移动更快。

如果再把伤害一起提高：

> 很难判断玩家觉得难，是因为密度、耐久、移动，还是伤害。

所以：

> **EC-01 先提高“战斗持续时间和场面压力”，不提高单次伤害惩罚。**

后续敌人技能/攻击威胁属于 EC-08。

---

# 14. 不改变敌人的架势值

EC-01：

- 敌人 HP ×2；
- 架势上限保持当前值；
- 架势伤害规则保持当前值。

原因：

这样玩家仍能较快制造破势窗口。

可以观察：

> 血量变厚以后，Break 是否开始比以前更有存在感。

这反而能为 EC-05 提供真实试玩依据。

如果同时把架势也 ×2：

> 会把 Break 暂时一起削弱，不利于判断。

---

# 15. 遭遇密度：不要简单把全图敌人总数翻倍

当前生成器：

> 每个 room 最多尝试 2 名敌人。

问题确实是单次遭遇太薄。

但 EC-01 不建议：

> 20个房间全部从2只改成6只，再加双倍血。

那样很可能只得到：

> 一张极长的血牛地图。

---

# 16. 推荐：减少“平均摊开”，增加“局部成组”

目标：

> **总敌人数只温和增加，但单场同时面对的人数明显增加。**

建议第一版 Encounter Tier：

### Safe
`0`

用于：

- Entry；
- 篝火周边；
- 必要过渡区域。

### Small
`3`

### Normal
`4`

### Strong
`4`，但必含更高威胁组合，例如：
- 1 Heavy + 2 melee + 1 ranged；
- 2 ranged + 2 melee。

EC-01 第一版先不做 5～8。

因为：

> 双人 + HP×2 已经是非常大的战斗压力变化。

如果试玩仍然稀薄，再进入 EC-01.1 把 Strong 加到 5～6。

---

# 17. 总敌人数预算

当前地图约 20 个房间。

建议不要让：

```text
20 × 4 = 80只双倍血敌人
```

成为默认。

第一轮目标：

> **大约 40～50 名总敌人，但集中成更有意义的 Encounter。**

也就是说：

- 一部分房间为空；
- 一部分用于篝火 / 过渡；
- 一部分是真正 Encounter；
- 单次遭遇人数从现在的约2提升到3～4。

具体总数由地图实际合法区域决定，但建议设一个明确上限，例如：

```text
standaloneEnemyBudget = 48
```

如果生成器发现候选不足：

> 少生成，不强塞非法点。

---

# 18. Encounter 房间选择仍然使用固定种子

保留当前：

```text
explorationSeed
```

同一 seed：

- Encounter 房间选择一致；
- 敌人位置一致；
- 敌人类型一致；
- 巡逻路线一致。

这样用户反馈可以写：

> seed 18，第 7 房间战斗太挤。

Codex 能稳定复现。

不要用裸 `Math.random()`。

# 19. Encounter 分布建议

不要求这次制作复杂 Encounter 编辑器。

直接基于当前 `map.rooms` 做确定性分层即可。

例如：

1. 排除 Entry / Campfire 安全区；
2. 根据 seed 打乱剩余合法 room；
3. 选定若干 Encounter room；
4. 分配 Small / Normal / Strong；
5. 总预算不超过约 48。

建议节奏大致：

```text
入口
→ 小遭遇
→ 空/移动
→ 正常遭遇
→ 篝火
→ 正常
→ 强遭遇
→ 空
→ 篝火
...
→ 出口前强遭遇
→ 出口
```

不需要这次做“正式关卡导演”。

只要避免：

> 每个房间机械地固定同样两只怪。

# 20. 敌人组合

继续只使用当前已有：

- melee；
- ranged；
- heavy。

EC-01 不新增敌人技能。

但 Encounter 可以通过比例变化获得一点结构。

### Small
例如：

```text

1 ranged
```

### Normal
例如：

```text
2 melee
1 ranged
1 melee/ranged
```

### Strong
例如：

```text

2 melee
1 ranged
```

不要每组都随机成完全不可读的组合。

# 21. 站岗 / 巡逻比例

继续复用当前：

```text
enemySense.home
patrol[]
```

第一版建议：

### Small
- 2站岗
- 1巡逻

### Normal
- 2站岗
- 1～2巡逻

### Strong
- Heavy 更偏站岗；
- ranged 可站岗；

# 23. 出口前 Encounter

当前出口本身是胜利条件。

EC-01 可以允许：

> 出口前有 Strong Encounter。

但敌人不能：

- 直接刷在出口圈里；
- 在玩家刚进图时通过全图寻路离开自己的 Encounter 区域。

仍然遵守当前：

- detect 5；
- lost 1.5；
- leash 8；
- 第一击入战。

EC-09 才重做伙伴 / Encounter 级行为。

# 24. 篝火不随双人化改变核心规则

三座探索篝火保持当前：

- 每处本探索一次；
- +50% max HP；
- 压力 -40；
- 技能 CD 清零；
- 满架势；
- 清虚血 / 硬直；
- 清普通负面；
- 不修耐久；
- 不复活死亡 / 濒死；
- 设置猎人复生检查点；
- 不刷新敌人。

但需要修正作用范围：

> **只对本次探索的猎人 + 被选伙伴生效。**
