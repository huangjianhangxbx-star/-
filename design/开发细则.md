## 0. 开工前的简明规则

- 每个新项目对话或独立执行者，完整读取本文一次；已完整提供且版本可确认的正文可直接使用，不为形式重复抓取同一内容。
- 同时核对适用的 `AGENTS.md`、任务范围与当前资料版本。之后按第 5 节补读，不每句话重读全部资料。
- `design/用户维护/` 是人工原稿区。AI 可按任务需要读取，但没有专项指令就不创建、回填、改格式、改名、移动或删除其中的文件。
- 用户选定一段设计并要求整理时，才把相应内容纳入游戏设计索引；不在每次开工时把所有 Excel 全量转成需求。
- 设计确认、计划批准、实现、验证、用户验收、原稿回填分别记录，不能合并成一个含糊的“完成”。
- Skill 按任务匹配，使用前核实真实可用并读取原文；目录中的名字和本文中的介绍不等于已安装或已使用。
- 普通实施任务按授权更新 AI 记录，不自动修改本文或人工原稿；提交与推送另按已批准策略执行。
- 归档历史不等于废弃现行规则；已经实现的现行约束必须仍能从索引找到。

## 1. 目录、文件与唯一职责

### 1.1 默认目录

所有路径相对于**项目根目录**。下图是职责约定，不代表每个文件已经建立，也不是读到就立即创建的指令。

```text
项目根目录/
├─ README.md
├─ AGENTS.md
├─ design/
│  ├─ 开发细则.md                    本文：整体制度 + Skill 使用规则
│  ├─ 用户维护/                     只放用户维护的 Excel 原稿
│  │  ├─ 书面游戏设计.xlsx           用户按自己的布局表达游戏设计
│  │  └─ 书面代码架构设计.xlsx       将来需要时由用户建立或专项委托建立
│  ├─ 游戏设计索引.md               AI 维护的唯一设计索引入口
│  ├─ 索引条目/                     索引较大、获准拆分时才使用
│  └─ 归档/                         获准归档的旧条目与历史版本
└─ docs/
   ├─ 项目状态.md                   当前工程状态摘要
   ├─ 规则对账.md                   设计/架构差异、决定与待回填事项
   ├─ tasks/                        实施任务、计划、验证与交接
   └─ 架构.md                       按需：从实际代码核对的现行架构
```

人工原稿区不放 README、AI 索引、日志、脚本、导出副本或审计报告。用户未指定创建的工作簿，不填空模板假装已有设计。Excel 自动产生的临时锁文件不算用户设计，AI 不以整理为由删除用户正在使用的文件。

旧项目可以保留 `记录/项目状态.md` 等路径，在 `AGENTS.md` 映射职责，不另造同职责的第二份主文件。**`design/用户维护/` 中的所有文件均受保护；旧版人工原稿在完成获准迁移前，也不得当作普通 AI 文档改写。**

### 1.2 职责分工

| 文件/区域 | 存什么 | 谁维护、何时更新 |
|---|---|---|
| `design/用户维护/*.xlsx` | 用户的人话设计、理由、构想、架构要求或用户记录的现状。允许长段落和自由布局。 | 用户；AI 只按专项创建/回填/整理指令修改指定范围。 |
| `design/开发细则.md` | 跨任务通用制度、读写与读取规则、Skill 选择规则及获准登记。 | 仅用户主动要求修改本文时更新。 |
| `design/游戏设计索引.md` | 用户已选入的设计主题、来源、精化要求、未决边界、相关任务及落实摘要。 | AI 在获准纳入设计或任务维护范围内更新。 |
| `docs/tasks/T-编号-名称.md` | 一次工程任务：计划、范围、批准、代码变更、验证和交接。 | AI 在相应计划保存/实施/验证授权下维护。 |
| `docs/规则对账.md` | 原稿、批准决定、索引和实现之间的差异；已批准待回填、待判断及解决记录。 | AI 在获准记录或实施任务内维护；不代替用户批准。 |
| `docs/项目状态.md` | 现在进行什么、可运行状态、验证范围、已知问题、下一步及任务链接。 | 有意义任务结束、中断或状态变化时，由获准 AI 更新。 |
| `docs/架构.md`（可选） | 经核对的实际模块、接口、依赖和重要技术限制；注明对应代码版本。 | 实际架构变化且任务允许文档维护时，由 AI 更新。 |
| `AGENTS.md` | 引用本文；登记真实路径、旧来源映射、工程命令、Skill 环境定位和获准项目补充。 | 初始化或工程配置变化时按授权维护；不可借改配置放宽人工区保护。 |
| `README.md` | 项目介绍、运行方法和资料入口。 | 相应信息变化时维护，不复制整本细则或规则。 |

术语、资产清单等可沿用已有文档，按任务读取。没有必要的资料时先说明缺口，不为凑齐目录批量创建空文档。

## 2. 权限与设计依据

### 2.1 人工原稿区：可按需读，默认不可写

“用户维护”表示写入归属，不表示 AI 不能读取。读取已选任务的相关原文和必要上下文，不需要用户每次重复授权；但不得因此扫描所有工作簿、转换全部设计或纳入无关系统。

以下操作均须专项指令：新增工作簿、修改内容/公式/批注/样式、插入编号、重排或增删工作表、重命名、移动、删除，以及用“导出/修复”工具重新保存源 Excel。泛泛的“继续开发”“完善记录”“按规范执行”“整理索引”不包含这些权限。

专项指令需能确定**哪份文件、哪个主题/区域、做什么改动**。不要求用户提供固定规则 ID 或精确单元格；用户可以指段落、标题、截图或贴出原文。位置无法唯一确定时先确认。

回填前核对最新原稿和预期旧内容，保留可恢复旧版本；原稿已被用户改动时，不用旧位置或旧批准盲目覆盖。格式无法安全保留时，给出局部修订稿，不能重建整本工作簿来替代。

### 2.2 常见任务的授权边界

| 用户本次要求 | 可以做什么 | 不自动包含 |
|---|---|---|
| 读取、讨论、检查、在聊天中出方案 | 相关资料读取、分析、给草稿。 | 写入项目、编辑 Excel、运行有副作用的程序或发布。 |
| 把选定内容写入/更新游戏设计索引 | 写指定设计条目和必要来源、对账链接。 | 开始实现、转换整本书、修改人工原稿或本文。 |
| “转换成索引”，但保存位置尚不明确 | 按项目已登记的保存约定操作；约定缺失时先给草稿并说明未写入，或确认位置。 | 把输出在聊天里的内容说成已入库。 |
| 按批准计划实施、修复或验证 | 相应代码/测试操作及任务、状态和受影响索引/对账的工程维护。 | 新增未批准玩法、编辑人工原稿、改变本文、无关资产改写或发布。 |
| 回填指定人工原稿 | 修改批准范围，并核对相关来源及回填记录。 | 顺便规范化整本、改其他主题或改代码。 |
| 修改《开发细则》指定规则或登记 Skill | 修改本文指定部分、版本标识和简要变更说明。 | 安装 Skill、改工具权限、实施游戏功能或自动升级其他项目。 |
| 提交/推送指定成果 | 核对范围后执行获准 Git 操作。 | Gitee 稳定同步、强推、重写历史、公开仓库等额外动作。 |

本表是项目协作约定，仍服从用户更窄的限制及平台实际权限。只读验证不自动包括会生成文件的测试或构建。已有长期授权须登记范围；未登记时不得假定存在。

### 2.3 三种事实分开判断

- **应该怎样：**本次适用的用户明确要求、未被撤销/替代的批准决定，以及相关人工原稿。原稿中的“暂定、可能、设想”不能当作最终批准。AI 提炼不是新的授权。
- **实际怎样：**相应版本的代码、配置和验证。原稿即使写着“当前已用某架构”，仍是用户的现状描述，涉及技术判断时需要核对代码。
- **允许做什么：**本次要求、已批准任务范围和有效工程授权。批准设计不自动等于允许实施、回填、提交或发布。

出现原稿与后续决定冲突时，逐主题比较内容、时间、适用范围和批准证据。记录“已批准待回填”只能补充其指定范围，不能无限覆盖后来被用户修改的原稿。先后关系不明时暂停受影响的实施，不凭文件名、修改日期或代码现状猜设计。

## 3. 人话 Excel 如何进入工作流

### 3.1 由用户选择内容，不由 AI 全量接管

触发方式包括：“把这个工作表里的卡牌段落转成索引”“只整理这段架构要求”“根据下面这段内容制定任务”。指令决定本次范围；同一范围内的必要澄清、后续状态维护不必重复授权，但跨入新的独立主题须说明并确认。

用户可以随时改变 Excel 的布局、标题、工作表和段落顺序。**不要求人工原稿一条规则一行，不要求用户写稳定 ID，也不要求事先建立固定列结构。**

### 3.2 从选段到实施的顺序

1. 定位用户指定内容，读取必要上下文；判断是游戏要求、架构目标、现状描述、理由、候选参数还是疑问。
2. 查 `design/游戏设计索引.md` 是否已有相同主题，核对相关 `docs/规则对账.md` 与历史批准，避免重复建号和重复确认。
3. 在获准范围内提炼成设计条目：保留原意、设计理由、不确定性与适用范围，列出 AI 增补的建议，不把解释冒充原文。
4. 仅澄清真正影响本轮的缺口。用户明确内容和已有有效批准不必全部重问；超出原意的关键补充需获得确认。
5. 获准保存索引/计划后写入相应文件。实施另遵循任务批准；读到原稿并不等于获准开始开发。

**提炼是语义整理，不是确定性格式导出。**可选工具能够提取单元格原文，但不能证明 AI 的分组、边界解释或推断已经被用户批准。不再强制建立全量“规则快照”和导出器作为每个任务的前置条件。

### 3.3 来源定位，不绑死单元格

每个设计条目记录：源文件相对路径、读取版本、当时工作表/标题、原文短摘录、已读范围；单元格范围是辅助线索。版本可用实际提交/文件指纹/明确上传版本标识，无法核验就注明。

段落一对多、来源多对一都允许。布局变化后按主题和原文重新定位；找不到或发现语义变化时标记“来源待核对”，不猜测新坐标，更不能仅因一行或工作表消失就认定设计废弃。

读取有合并单元格、图片、批注、隐藏内容、公式或外部引用的工作簿时，说明实际覆盖。工具不支持的部分不得声称已读。用户提供局部文本或截图时，可以按该范围分析，但不说已经读取整份 Excel。

网页只看到远端版本，不能假定包含用户本机尚未保存/推送的修改。已有清楚且仍有效的索引可以支持无冲突任务，不要求每次打开原始大表；修改设计语义、来源已变、涉及回填或来源不可靠时必须补核相关原文。

### 3.4 新增《书面代码架构设计》或其他人工 Excel

新增文件一进入人工区，就受同一写保护。是否读取、转成条目或任务，仍由用户本次选定内容决定。索引为条目标注类型，例如“玩法”“架构约束”，无需另造一套任务制度。

架构原稿可同时写“希望采用的架构”和“用户认为目前采用的架构”。AI 在索引中分开保留；实际现状以核对的代码和 `docs/架构.md` 为证据。纯重构任务记录必须保持的行为；涉及玩法改变要单独提出，不能藏在重构名义下。

具体文件路径登记到 `AGENTS.md`；用户要求增加一种新的读写制度时才修改本文。用户也可以主动要求在本文增加新原稿类型的说明，但 AI 不因发现新 Excel 就自行改细则。

## 4. 游戏设计索引、任务编号与历史整理

### 4.1 索引不是用户原稿，也不是任务流水账

`design/游戏设计索引.md` 为唯一入口，开始时可在一份 Markdown 中记录全部已选主题。每个条目最少有：

| 内容 | 要回答什么 |
|---|---|
| 身份与主题 | 如 `D-001`，类型为玩法/架构等；用户不负责分配 ID。 |
| 来源与适用范围 | 来自原稿哪里、哪个版本；本条覆盖什么、不覆盖什么。 |
| 要求与不确定性 | 明确要求、理由、边界，以及独立标出的待确认建议。 |
| 决定状态 | 原文要求/待确认补充/用户已确认/获准试验/已废弃等，按实际证据填写。 |
| 落实摘要 | 未开始、部分落实、待验证、在指定范围及版本已验收；关联任务与证据。 |
| 对账和来源状态 | 已核对、来源待核对、相关待回填/未决变更链接。 |

只有进入当前工作范围的主题需要精化。一个主题可以有若干验收条件，不为每句话分 ID。实现需要独立追踪时再拆分；原文不会被强制改造成结构化表格。

### 4.2 设计 ID 与任务 ID 不混用

设计 ID（示例 `D-001`）代表要求；任务 ID（示例 `T-021`）代表一次工作。旧项目已有 `R-*` 等设计编号可继续使用，不强制重编。

一个设计可由多个任务实现，一个任务可关联多条设计。关联说明是“实现”“修复”“验证”还是“保护既有行为”。纯工程重构、构建修复或测试任务可以没有新增设计 ID，不编造玩法需求凑编号。

任务完成不意味着设计已废弃或整个系统全部完成。返回给用户的落实摘要应按原稿主题说明“本轮做了什么、没有包含什么、验证到什么程度、是否需要回填”，而不只报告编号关闭。

### 4.3 不无限堆积，也不删除现行约束

- **仍然有效且已经实现的设计：**保留简短现行条目和验证链接；完成不是删除条件，后续重构仍需这些约束。
- **已完成任务的详细过程：**可移到 `docs/tasks/归档/`；索引保留关联。当前状态只保留结果摘要，不重复全文。
- **已废弃/被替代的设计及旧修订：**可移到 `design/归档/`，入口保留 ID、处置原因、替代项及可访问链接。
- **条目较多：**用户批准整理后，将正文按系统放入 `design/索引条目/`，主文件保留导航和活动事项。拆分索引不需要拆分本细则，也不要求新开人工 Excel。

默认先提议整理，不擅自大规模迁移。用户明确说“按细则整理并归档”时，可按上述非破坏方式操作并报告路径。物理删除需明确对象及授权，先核对活跃引用和恢复途径；“整理”不等于删除。

ID 不复用给其他含义。新开索引或重排条目须保留唯一入口、历史定位与关联，不把旧任务全部变成断链。归档路径需要时才创建，不设每日/每周强制整理要求。

## 5. 何时读取：新对话全文，后续按阶段和变化补读

### 5.1 新对话/独立执行者的基础读取

### 5.3 重读触发与控制负担

| 触发 | 处理方式 |
|---|---|
| 同一任务连续追问，资料和权限没变 | 复用当前可靠上下文，不重复全文读取和长篇复述规范。 |
| 同一对话开始另一个任务 | 核对规范/AGENTS是否变化、活动状态、任务范围；检查上表对应章节和 Skill 登记。未变全文不用再读。 |
| 从讨论转实施，或从实施转回填/发布 | 重新检查相关权限和阶段规则；旧授权不足就确认，不把“继续”无限扩大。 |
| 本文改变 | 在下一次相关工作前完整重读新版本；只有一个文件，不只看新增 Skill 而遗漏其他边界。 |
| AGENTS、分支或工作树改变 | 核对新版本规范/映射/授权，读受影响配置和资料；不机械重读无关内容。 |
| 用户说人工 Excel 刚改过 | 补核本次主题相关原稿；变动无关则沿用未受影响部分。无法确定时说明来源待核对，不自动全量转化。 |
| 新代码提交或本地修改 | 读取对应差异、任务结果及受影响设计，不把过去的验证用于新代码。 |
| 换执行者、上下文压缩后关键规则不可见、无法确认记忆完整 | 重做基础读取并读当前任务批准与交接。独立子代理获得同版完整规范、相关任务及更窄权限，不假设自动继承。 |
| 选用一个新 Skill，或该 Skill 原文/版本变了 | 读取该 Skill 的真实 `SKILL.md` 及必要依赖；同版原文仍完整可用时不反复加载。 |

“检查”不一定每次都重新发起文件请求；完整内容和版本仍可信时可以据当前上下文核对。无法核对远端变化时直说，不宣称持续监听。不要设每隔几分钟重读或每条消息重读的机械规则。

新对话仅需短报：**规范版本、代码/资料基准、任务范围、拟用 Skill、权限边界、缺失项**。这是事实摘要，不是宣誓或伪造“已读检查表”。

## 6. Skill 使用规则与登记：保留在同一份细则中

### 6.1 一个文件分章节，不复制技能全文

本文说明**什么时候考虑什么 Skill、何时必须使用、你如何手动提醒**。具体执行步骤以当前可用的真实 `SKILL.md` 为准，必要时继续读取它明确要求的资源。

相关产品目前采用先呈现技能名称/描述、选中后加载完整说明的方式；具体机制和入口应以当时官方说明及当前工具为准。[1][2] 因此不把十几个 Skill 全文塞进本文，也不要求每次任务把所有技能打开一遍。

**本文登记不等于安装、发现不等于读取、读取不等于执行、执行不等于验证成功。**不同客户端可用能力须分别检查；不要根据另一台设备的安装状态作保证。

### 6.2 每个阶段如何选择

在需求精化、计划、实施/调试、验证/审查、回填或制度维护的阶段开始时：

1. 判断当前任务目标与阶段，匹配登记中的使用条件与排除条件。
2. 核对当前环境真实可用的 Skill，必要时使用实际提供的发现入口；同名技能要区分来源，不只按显示名猜。
3. 使用最小必要组合。步骤不重复覆盖；选中后读取真实说明，再按必要依赖补读。
4. 简短说明本阶段使用什么及用途，不为每个命令反复报告。未用、不可用或仅采用相似方法，要明确区分。
5. Skill 的默认流程不能扩张本次权限。要求改原稿、装软件、推远端、删除文件或偏离批准设计时，先处理授权与冲突，不借 Skill 之名执行。

平台明确要求的技能或安全流程按其实际要求执行。下面的项目登记只补充选择偏好，不禁用更高层要求，也不能放宽保护边界。

### 6.3 三类触发策略

| 策略 | AI 应如何执行 |
|---|---|
| **匹配时必用** | 当前任务命中且环境可用时必须按说明使用。不可用/不兼容时说明影响；改用替代方案需符合用户已批准的替代策略，否则先确认受影响步骤。 |
| **匹配时优先** | 符合任务且有帮助时采用；不适合时可用现有工具完成，简要说明，不每次都问用户。 |
| **仅手动** | 仅用户本次明确指定时使用，不因为名称相近就自动调用。 |

在平台和本次授权允许范围内，未登记的已有技能仍可按任务需要使用；不能自行把它永久加入本文。没有适合技能就用正常流程，不为了“符合细则”强套一个 Skill。

### 6.4 Skill 登记模板

**下面是通用登记模板，不是现成安装列表。**第 6.5 节另列 Grill with Docs 的待核对登记，尚未确认用户所装版本，也未启用自动触发策略。每个常用 Skill 保持简短，实际运行日志另写任务记录。

```markdown
### <技能的准确名称>
- 能力简述：<解决什么问题；不是泛泛的“提高效率”>
- 来源与适用端：<插件/仓库/本地位置等明确标识；Chat/Work/Codex等实际适用端>
- 何时使用：<阶段 + 可以判断的触发条件>
- 何时不使用：<排除场景，避免过度触发>
- 触发策略：<匹配时必用 / 匹配时优先 / 仅手动>
- 手动提醒：请使用 <准确名称> 处理 <具体任务>。
- 快捷入口：<在对应端实际核验的命令/选择器；未核验写“待核验”>
- 预期产出：<澄清清单/计划/测试证据/审查结果等>
- 不可用时：<获准替代方法或需用户确认的边界>
```

快捷入口因客户端而异。官方当前说明 ChatGPT 可通过 `@` 选择技能，Codex CLI/IDE 可通过 `/skills` 或 `$` 提及技能；记录实际名称和适用端，不能把一端命令写成通用命令。[1] 不知道入口时使用自然语言明确指定，不虚构命令。

“使用情况”在本文指**适用场景与长期策略**。某次是否加载成功、运行了什么、缺哪些依赖，记在对应任务文件，不为一次成功/失败修改本文。用户要求更改长期策略时，才更新本节。

### 6.5 Grill with Docs：待核对的登记草稿

**登记不等于安装或调用。**用户已说明经常使用该名称的技能；当前没有拿到用户实际安装的 `SKILL.md` 与相关配置。本条以已查阅的公开候选 `mattpocock/skills` 为参考，不把它认定为用户所装版本，不替用户更换技能来源。确认前不得声称“已核实安装”“已使用该技能”或“已启用自动调用”。

#### A. 公开候选中核实到的内容

| 项目 | 内容 |
|---|---|
| 名称 | 显示名 Grill with Docs；候选技能标识 `grill-with-docs`。 |
| 公开候选来源 | `mattpocock/skills` 的 `skills/engineering/grill-with-docs/`。本次查阅的是公开 `main` 页面，不是用户本机的固定版本。[5] |
| 能力 | 将计划／设计的追问澄清与领域概念整理组合起来，在过程中形成术语与必要的设计决定记录。[5][6] |
| 依赖 | 该候选的入口要求调用 `grilling` 和 `domain-modeling`；正式使用前还须核对并读取它们的真实说明及所需资源，不能仅凭一个同名入口文件声称完整可用。[5][6] |
| 原生触发限制 | 该候选含 `disable-model-invocation: true`，其 `agents/openai.yaml` 含 `allow_implicit_invocation: false`。在支持该策略的 Codex 中，后者表示不根据任务隐式调用；明确调用仍可使用。[5][7][8] |

公开候选的说明不能证明用户所装版本完全相同。正文、依赖、提问节奏及写文档行为，应以最终核实的那一版为准；不要拿其他同名版本或 `grill-me` 顶替。

#### B. 建议的项目使用约定（尚待用户确定长期策略）

- **建议使用阶段：**用户选定原稿并需要澄清歧义时；新机制或架构方案存在关键边界、术语冲突或设计取舍时；正式计划批准前需要检查隐含假设时。
- **不默认使用：**闲聊、明确的小修、格式修改、同一任务已确认问题的重复提问，以及已批准计划的每一个编码步骤。出现新的关键设计问题时再判断。
- **触发建议：**匹配时提示适用性，用户明确指定后使用。用户所说“经常使用”不自动等同于“所有任务必须使用”。以后需要自动触发，须单独核对客户端能力、技能原生策略与用户授权；只修改本细则不能更改原生配置。
- **输入范围：**本次选定的原稿／设计索引或计划，相关规则对账、术语说明、实际代码与必要测试；按第 5 节取相关部分，不全量扫描人工原稿。
- **预期产出：**待决问题、明确决定与未确认建议、相关术语、值得保留的取舍及必要的计划修订建议。澄清完成不等于批准实施，也不等于最终任务单已经保存。
- **项目写入边界：**默认仅在聊天中澄清、给出文档修订稿。只有本次已获准文档维护时才实际写入；沿用 AGENTS 指定的职责路径。用户维护区 Excel 和本细则仍须专项授权。技能建议更新术语或决策文件，不代表可以自动创建第二套索引或回填人工原稿。
- **术语与决定分开：**沿用现有术语文件；存在 `CONTEXT.md` 时，核对其在本项目的用途。候选技能将它作为术语表，不能把完整功能规格或任务流水账塞进去。架构决策记录（ADR）只在有必要且获准记录时建立，不为每个小决定增加文档。[6]
- **不可用或不兼容：**说明实际缺少的说明、依赖或工具。可在用户同意后采用类似的问答方法，但需说明这是按可用资料进行的人工流程适配，不是完整调用已安装技能；不为执行技能而擅自安装、改权限或放宽保护规则。
- **手动提醒：**“请使用你实际安装的 Grill with Docs 澄清这段设计。先核对来源、依赖和真实说明；只讨论，不改人工 Excel、开发细则或游戏代码。文档写入按本次明确授权执行。”
- **快捷入口：**用户当前客户端入口尚未实测。已识别该技能的 Codex CLI／IDE 可用显式技能提及方式；其他端须以其真实选择器和安装情况为准，不把某一端命令写成通用命令。[1][8]

#### C. 正式登记前只需补核一次的内容

取得用户实际使用的 `SKILL.md`；若有 `agents/openai.yaml`、被引用的子技能或其他必要资源，一并核实。记录准确来源与可验证版本，替换本条的候选说明；由用户确定长期触发策略。只改本次登记及相关交叉引用，不安装、不启动澄清会话、不修改其他制度。以后按第 5.3 节在版本变化或上下文不可靠时补核，不要求每个小任务重新安装或全量检查技能库。

## 7. 开发、记录、回填与同步

### 7.1 单次任务的闭环

```text
用户选定内容/提出问题
    → 读取相关资料，选择适用 Skill
    → 整理/核对设计条目，澄清必要歧义
    → 制定并批准本轮任务范围与验收
    → 获准保存后，执行者核对实际代码并实施
    → 验证，更新任务/状态及受影响索引、对账
    → 按授权保存到 GitHub，交给下一端看指定版本
    → 用户试玩/审查后继续修正或确认本轮可用
    → 仅在专项指令下回填原稿；仅在发布批准后同步 Gitee
```

纯工程任务不强制先修改设计索引或人工原稿，可以直接关联已有约束并制定任务。没有新内容的闲聊不创建任务文件。同一任务的小修可续写，不每条对话新增编号。

任务文件至少记录：目标与非目标、设计/工程依据、实际基准版本、批准范围、实施计划、验收方式、真实改动、验证结果、剩余问题和交接状态。不要让详细工程字段成为用户写原稿的要求。

有意义任务结束或中断时，获准执行者更新任务和当前项目状态；索引只更新受影响条目的落实摘要/链接，对账只更新真实新增差异。没有写入授权或工具时，交付标明“待保存”的记录，不能说已完成入库。

验证注明通过/失败/未执行、命令或操作、环境与受测范围。受测时有未提交内容，不能单用旧提交号代表它；后来改代码要重新判断旧证据适用性。最终提交号可在交接回复中给出，不为把最终号写回报告自身无限生成新提交。

### 7.1.1 原型迭代期的验证分级与成本控制

**适用范围：**本项目仍处于玩法、手感、UI、美术及暂定参数快速迭代的原型阶段时，验证以“确认本次改动可用、核心行为未倒退”为主，不以每轮达到正式发布质量为目标。初次任务计划明确选择验证等级与理由；用户专项验收、重大真实风险和更高优先级要求优先，不因默认分级而失效。后续进入正式发布阶段，可另由用户批准发布级门槛。

| 等级 | 默认使用场景 | 最小必要验证 | 原型期通常不做 |
|---|---|---|---|
| **A｜快速验证（默认）** | 单点数值、文案、局部视觉、已有功能小修、尚未定稿的表现试验 | 仅相关自动测试；运行时代码有变更时，验证受影响的实际入口与关键操作；纯文档/未接入资产可以只检查文件或预览 | 全量核心/全量浏览器、多分辨率长流程、整套历史回放、跨仓库大规模冻结 |
| **B｜模块验证** | 体力、角色技能、敌人伤害、AI、UI 信息绑定等一个完整系统的开发 | 受影响的模块与共享权威测试；适用时执行类型检查/构建；少量真实键鼠或浏览器场景覆盖成功、失败和必要生命周期 | 与任务无关的旧塔防、旧入口、全套历史 UI 与完整地图逐项回放 |
| **C｜阶段/高风险验证** | 架构迁移、跨模块核心改造、重大生命周期/经济一致性、交付里程碑、用户明确要求全面验证 | 按实际受影响范围扩大逻辑/浏览器/资源回归；明确风险矩阵、通过与未覆盖部分，必要时进行多场景和多分辨率实测 | 无理由地把全部退休系统和所有历史用例当成每次必过条件 |

**选择与升级：**原型任务一般从 A 开始判断；确实触及共享伤害结算、输入所有权、场景/资源生命周期、奖励唯一性等关键权威时升至 B，波及多项不可隔离的核心契约或重大阶段发布时再考虑 C。用户已批准的专项验收（例如按 PPT 严格还原布局并核对三档尺寸）不能被默认 A 级取代；大型功能也不因代码行数少就自动算 A 级。

**时间成本：**A 级验证可按约 5～10 分钟、B 级约 10～25 分钟安排初始验证预算；这是**规划参考**，不是硬性超时或掩盖失败的借口。C 级需在计划中单列验证范围及时间成本。预计明显超出预算时，先区分是真实产品问题、环境/测试夹具问题，还是新增了非必要验证；优先完成相关必要检查，简短报告延时原因，而不是无限扩张套件。

**增量验证原则：**编码中优先运行相关小集；代码/契约稳定后根据所选等级执行最终验证。仅测试选择器、等待时序、旧 UI 位置假设等夹具错误，先保留真实失败证据，再对该项定向修复与复测；不因测试脚本本身的小改动机械重跑全部浏览器用例。修改了共享运行时或出现新的实质回归时，按影响范围扩大测试。不得为得到全绿而静默删除、跳过、放宽有效业务断言或把分段通过写成“一次完整全绿”。

**未定稿内容与关键底线：**临时美术、手感、SAMPLE 平衡和布局候选不要求提前建立严格像素快照或大量永久断言；用户试玩/审美判断与技术测试分别记录。但受影响的启动可用性、真实操作、碰撞/攻击和伤害、格挡闪避、状态/资源不重复结算、世界离开/继续、角色身份和必要错误反馈仍须按相关风险验证，不允许隐瞒真实缺陷。没有关联影响的退休功能不成为日常原型开发阻断条件；仍有效的保护性测试按实际依赖保留。

**轻量交付与保护不变：**交接简要记录验证等级、执行过的检查及结果、未执行项目、已知风险、用户尚待试玩事项即可。禁止为每个微小任务默认全量复制历史验证产物、扫描并冻结数千无关文件、输出大量相同截图；只保存能够支撑本轮结论的必要证据。`design/用户维护/`、本文及其他未授权文件的保护、未提交工作保留、按批准范围 GitHub 提交、Gitee 限制和用户试玩 Gate **继续按本细则其他章节执行，不因降级验证而放宽**。

### 7.2 对账与专项回填

| 情况 | 记录与处理 |
|---|---|
| 按已有设计实现，没有改变设计 | 更新任务和落实摘要；原稿无需修改。 |
| 用户批准新规则，但人工原稿尚未改 | 在 `docs/规则对账.md` 记录适用范围、准确决定/批准依据、原稿位置、关联设计/任务和“已批准待回填”。 |
| 代码出现未批准的新行为 | 记“待判断差异”；不能以已实现、测试通过或用户没反对为批准。 |
| 行为违反已确认要求 | 按获准范围修 Bug；不修改原稿迁就实现。 |
| 用户批准回填 | 再核对最新原稿，给出并应用批准范围的局部修订；核对索引来源和对账状态，不改其他主题。 |

对账条目保存准确内容，不只留下一个可能打不开的聊天链接。用户可用标题、原文或截图指定回填，不必记 ID。已回填须实际核对，不能因为任务完成而自动关闭；回填也不证明实现完成。

### 7.3 GitHub、Gitee 与文件保护

GitHub 保存开发阶段，Gitee 保存用户批准的稳定版本，是本项目使用约定，不是平台天生的内容差异。每个有意义阶段可按授权提交推送，不必逐行上传。

推送前检查实际文件范围、目标远端/分支和已知问题。**人工原稿区的“禁止 AI 改写”不等于不备份。**用户保存的 Excel 可以按已授权备份范围提交；若不属于当前任务或发布许可不明，先确认是否纳入，不能因 `git status` 显示改变就全部提交。

本次没有原稿写入授权时，收尾检查保护区和本文是否被 AI 意外改动。发现差异须区分用户原有修改与 AI 产生修改，不一键还原用户工作。可用只读限制或检查脚本加强保护，但只有实际配置验证后才能说有技术拦截；本文自身不是文件锁。

网页与本地交接至少包含：任务文件路径、计划版本、目标分支/提交、批准范围和已知问题。同步前先查本地未提交内容，不强制重置；接手方读取实际目标版本，不沿用过期摘要。

GitHub 推送不自动更新另一段聊天的理解。Gitee 同步仅针对获准版本和引用，不自动备份所有分支、标签、忽略文件或外部资产。失败保留本地成果并说明，不自动强推或清理历史。

## 8. 本文维护、项目配置与首次接入

### 8.1 什么需要更新本文

只有用户明确要求改变制度、登记/调整常用 Skill、增加人工资料类型的特殊处理规则时，AI 才修改本文。流程中发现改进点，可提出建议或在任务记录待议，不自行修改长期规则。

更新时保留单一入口，改指定内容并检查相关章节是否矛盾，更新版本；大改需给出影响说明。Skill 安装状态、每天进度、代码版本、个人任务结果不写进本文。不同项目采用哪版由用户决定，不假定其他项目同步升级。

本文分章节但不拆成“整体细则.md”和“Skill细则.md”。若将来登记过多，先压缩描述和移除已获准停用的登记；详细 Skill 原文始终在其真实位置。只有用户明确认为规模过大时再讨论拆分，不预先增加维护文件。

### 8.2 AGENTS 和 Project Instructions 的接入

`AGENTS.md` 保留简短入口和本项目配置，不复制全文。Codex 的指令发现与加载有自身规则，提到文件不等于已经全文读取。[3]

以下片段是接入示例，**须与已有配置核对后再写入，不覆盖原文件**：

```markdown
## 协作规范入口
本项目采用 design/开发细则.md（启用版本：<实际版本>）。
每个新项目对话/独立执行者先完整读一次，随后按第5节补读；
各阶段按第6节匹配实际可用Skill，使用前读真实说明。

design/用户维护/ 是受保护的人工Excel原稿区。
普通开发/记录授权不允许改写该区域或 design/开发细则.md。
用户选定内容后才纳入索引；不进行默认全量转换。

## 本项目真实配置
- 设计索引：<实际路径；默认 design/游戏设计索引.md>
- 项目状态：<实际路径>
- 规则对账：<实际路径>
- 任务目录：<实际路径>
- 人工来源：<实际存在的Excel路径；未建立写未建立>
- 未迁移的旧设计来源：<模块、文件和有效范围；无则写无>
- 代码/测试/架构入口：<实际路径>
- 构建/测试/启动：<实际工作目录、命令与前提>
- Skill环境定位：<可验证的来源/位置；不把未核实内容写成已安装>
- GitHub与Gitee：<真实远端、分支及用户授权策略>
```

ChatGPT 项目说明可使用下列短入口。项目说明作用于相应 Project；它不会自动把仓库文件复制给本地或加载全部相关内容。[4]

```text
项目仓库：<实际 owner/repository>。
每个新项目对话，请完整读取 design/开发细则.md，核对适用 AGENTS.md，
再按细则第5节按场景读取，第6节选择真实可用的Skill。
用户维护区的Excel和开发细则本身，只有专项指令才允许改写。
不要全量转换人工原稿；只处理我选定或已批准任务涉及的内容。
来源不可访问、版本不能核验或工具不可用时直接说明。
```

入口必须实际保存并按需要推送才会生效；不保证 AI 永不遗漏。可通过开工摘要、任务阶段权限检查、收尾差异检查降低偏离风险；更强的技术约束另作为工程任务配置。

### 8.3 旧规范与旧资料如何迁移

新启用本版时，检查 AGENTS 和旧说明中的冲突：删除“用户必须填写稳定ID列”“每次全量导出规则快照”“AI自动回填原表”等旧约束；修改须属于用户批准的接入范围。

旧 TXT、`CurrentRules.md`、规则修订、旧交付报告等先保留，登记各自的有效范围和历史身份。用户只选一个主题迁移时，不全量重写旧资料；新的 Excel 尚未包含某主题，不代表该主题被废弃。

旧结构化总表可在用户决定后作为 AI 索引迁移来源，不要求用户继续填它。旧导出工具不再是本版默认前置条件；仍在使用时按真实用途保留，不自动卸载或删除。

当前任务无法访问原稿时，可以使用用户指定片段或已有有效索引进行限定范围的工作。关键语义冲突或回填原文无法核对时，只暂停受影响步骤，不把缺少自动化扩大为全部任务无法开展。

## 9. 用户可以直接使用的提示语

以下是按需要使用的示例，不是 AI 读到就立即执行的命令。

**新对话：**“先完整读取 `design/开发细则.md`，按 AGENTS 找到当前资料。告诉我本次基准、相关已读范围、拟用 Skill 和限制；暂时只读。”

**选段转索引：**“读取 `design/用户维护/书面游戏设计.xlsx` 中我指出的这段，保留原意与待定之处，只更新对应游戏设计索引条目。不要转换其他主题，不改 Excel，不开始实现。”

**架构任务：**“读取我选中的书面代码架构设计，区分目标和现状，核对真实代码。整理对应架构约束和任务计划，暂不实施，不更新人工原稿。”

**手动提醒 Skill：**“本阶段请使用 `<准确Skill名称>` 做 `<任务>`。先核实当前可用并读其说明，不改变本次读写权限。”

**整理索引：**“按细则整理并归档过期修订、已废弃设计和完成任务的详细过程。保留现行已实现要求的简短条目与引用，不物理删除，不动用户维护区。”

**回填原稿：**“把本轮我明确批准的这几项变化回填到指定工作簿对应段落。先核对原文和拟改内容，只改这些位置，不重排布局、不插入编号。”

**更新细则：**“只修改开发细则第6节，将 `<准确Skill名称>` 登记为 `<触发策略>`，条件为 `<场景>`。核对能力与实际入口，不安装，不修改游戏代码或人工原稿。”
