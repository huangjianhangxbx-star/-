## 0. 先把这次用户真正想要的事情定清

### 0.1 用户在当前截图中明确要求

1. 「项目与资产」页面目前非常难用，不能继续使用横向铺开多个信息贫乏的「未命名」卡片作为主工作流。
2. **草稿必须能删除**；**场景必须能删除**；**项目/场景/草稿模块必须能方便地改名**。创建后不能无处删除。
3. 创建、浏览、重开、修改、另存、找回资产应该符合普通桌面制作工具的操作直觉，不能需要猜「编辑模块」「独立副本」「登记到公共库」之间的差别。

### 0.2 用户附带的最新开发讨论还明确提出的产品方向

4. 3D 工坊的核心定位是**体素风格独立模型的生产工具**；每个独立原生工坊资产才是主角。
5. **保存原生工坊资产**和**输出外部 FBX 成品**要分开：工坊内部继续保存可编辑源，导出 FBX 后不会随着后续草稿编辑自动改变。
6. 「项目与资产」应能记住最近项目，能一键再次打开，不必每次重新选目录。
7. 工坊资产库依据项目目录组织，显示原生工坊资产，并为资产提供可视化缩略图、名称及路径。用户能选保存位置、为资产命名，保存或另存新资产后立即出现在库中。
8. 「场景装配」降级为**引用工坊资产的试摆预览**；编辑同一源资产，试摆中引用它的实例应同步更新。场景组合仍可以命名、保存、预览、一键重开。
9. 不再以发布整张场景为目标；对外主功能是**导出当前独立资产的 FBX**。GLB 如果仍作为内部转换中间产物，可以隐藏，不再让用户做无意义的外部格式选择。

**重要区分：**第 1—3 项是当前应优先消除的使用障碍；第 4—9 项是新产品定位。两者相关，但不是同一个小修。推荐本计划分成**可独立交付的三个实施包**：
- **A／立即变好用（P0）：**改名、删除/恢复、最近项目、卡片/列表层级与基本预览。
- **B／资产优先（P1）：**原生资产变为项目级主数据；试摆只引用资产，不在每次放置时复制源；旧项目安全迁移。
- **C／制作闭环（P1）：**资产编辑器一键导出 FBX；简化试摆草稿；从正常 UI 移除整张场景「发布」。

**不可把 B/C 未完成写成 A 已经解决。**A 必须独立可用，用户可在 A 完成后实际试用；B/C 需在 A 稳定后继续执行同一批准范围内的计划，若发现影响既有用户数据的取舍必须停下确认。

## 2. 最终产品应该呈现的心智模型

原来：**新建项目 → 先建场景 → 在场景里建草稿 → 编辑模块 → 复制/公共库 → 装配 → 发布场景或模块**。
目标：**打开最近项目 → 新建/选择原生资产 → 编辑 → 保存原生资产 → 导出单件 FBX**；可选「到试摆场景看看」，试摆草稿只记录哪些资产放在哪里。

### 2.1 普通用户界面架构（建议）

主导航由「项目与资产」「模块编辑」「试摆场景」构成；原「发布」工作区不再出现在**新模式**的正常导航，改为模块编辑器中明确的 **「导出 FBX…」**。旧模式/历史冻结包可以保留只读或兼容入口，不能直接删掉已有发布数据和引擎代码。

**项目与资产主页：**

```text
星骸工坊 / 当前项目：墓穴资产组             [保存 Ctrl+S] [打开项目▼]
┌ 最近项目（最多10~12项）────────────┬─────────────────────────────────────┐
│ 最近：墓穴资产组 [一键打开]         │ 资产库   [新建资产] [导入] [搜索]      │
│ 最近：露天废墟   [一键打开]         │ ┌─────────┐ ┌─────────┐ ┌─────────┐ │
│ 缺失：样板间     [定位/从历史移除]   │ │缩略图    │ │缩略图    │ │缩略图    │ │
│                                    │ │石柱 A    │ │断墙 B    │ │木箱 C    │ │
│ 当前项目                           │ │已保存    │ │未保存    │ │已保存    │ │
│ [资产] [试摆场景] [回收区]         │ │编辑/导出 │ │编辑/更多 │ │编辑/更多 │ │
│ 场景：墓穴试摆、外墙试摆            │ └─────────┘ └─────────┘ └─────────┘ │
└────────────────────────────────────┴─────────────────────────────────────┘
```

资产卡片主按钮只需「编辑」「导出 FBX」「⋯」；「⋯」提供改名、另存新资产、复制、定位本地源、移入回收区。场景列表提供打开、改名、复制、移入回收区。不要让每张卡固定铺三个不解释含义的操作按钮。

界面必须有**明确的当前项目名称与路径、最近保存时间、已保存/未保存状态、选中场景、空状态建议操作**；默认卡片有真正模型预览，不只是数字和「未命名」。

### 2.2 名词必须清楚

- **工坊原生资产**：可继续编辑的体素数据/颜色/Root/元数据（现有 `AssetDocument` 格式可作为迁移输入）。
- **资产副本**：用户明确「另存为新资产」产生的新稳定 ID，修改副本不影响原资产。
- **场景试摆**：保存原生资产 ID＋位置/旋转/分组的工作草稿，不是需要对外发布的地图文件。
- **导出 FBX**：对外静态成品及必要材料旁车/贴图依赖；之后保存原生资产不会暗中覆盖之前导出的 FBX。
- **回收区**：项目内部可恢复的已移除原生资产/试摆场景；不是公开资产库，也不是已导出的 FBX。
- **外部公共库**：保留从外部位置**导入/拷贝为项目资产**的能力；不要求每次装配都先创建独立副本。两种动作名称区分清楚。

## 3. A 包：先把项目管理修好（P0，优先独立交付）

### A0／实施前的安全基线

- 当前 `main`、本地 HEAD、工作树、运行 EXE/启动脚本、`project.xhproject.json` 格式和用户现有项目位置全部核验。
- 选至少两份**备份副本**作为测试项目：一份多场景/多体素模块，另一份有非空实例、PNG/GLB引用或发布历史的复杂工程。没有现成用户测试副本时，用原创测试项目，不拿用户真实工程做首次破坏性实验。
- 记录工作树未提交差异并保护其他任务，特别是 TOOL-007 的进行中修改；不要 reset、clean、强制结算并行改动。
- 验证当前 Scene/Asset 在同一实例下的身份、引用与 Dirty/Save 语义。锁住基线 SHA 和可回滚副本。

### A1／改名（必须完成，且入口可见）

1. **资产改名：**卡片上 F2 或「⋯ → 重命名」与模块编辑页 `#module-name` 双向同步；利用现有 `manager.rename`，不引入第二套名称权威。重命名后卡片、编辑页 Tab、装配列表立即更新，保存重开后保持。
2. **场景改名：**场景侧栏支持双击或 F2/「⋯ → 重命名」；同一事务更新 `SceneDocument.name` 和 `ProjectDocument.scenes[].name`，避免标题一处改、一处不改。场景 ID、目录名、实例和原有发布快照保持不变。
3. **项目改名：**标题处提供可发现入口，更新 `ProjectDocument.name`；不强迫物理改项目文件夹。
4. 创建新草稿时尽量自动生成可识别默认名（如「新模块 01」），并把命名输入作为新建后可跳过的快捷动作；不要求用户填写 ID。
5. 空名/纯空白/Windows 不合法字符/重名的策略：展示名称允许合理重名但**同一项目建议显式提示重复**，实际路径始终用不可变 ID，不依赖显示名称；避免重命名后引用丢失。
6. Escape 取消改名不改数据；Enter 提交；弹窗打开时保留键盘焦点；输入框 Ctrl+Z 不误撤销场景。

### A2／删除草稿与场景：有恢复能力的真实操作

**首选设计：默认「移入回收区」而非立即不可恢复删除。**这不是取消删除功能：从正常列表立即消失，存储保持可找回；回收区提供「恢复」「彻底删除」。

- **未落盘的新草稿：**删除时移除内存会话与目录登记，触发正确的 Dirty 与 UI 刷新；无需制造不存在的磁盘垃圾。
- **已保存的私有模块：**检测 `SceneDocument.instances`、`decals`及其他引用，不允许只删文件留下缺失引用。若被使用，弹窗显示**具体使用次数与所属场景**，默认提供「取消 / 查看引用」，可在用户明确确认的情形下先移除相关实例或选择「复制源后改指」，不可暗中删除。
- **删除场景：**确认页显示场景名、实例数量、私有模块数量、是否有未保存修改；删除后自动切换到邻近场景或空项目提示。旧版私有资源跟场景一同存入回收区；新模式下独立项目资产绝不因为删除试摆场景而被删。
- **回收区恢复：**恢复原 ID、源路径和引用；恢复时若目标已被占用或版本变了，明确冲突，不覆盖新内容；彻底删除必须二次确认。
- **撤销/恢复界限：**删除**未保存项目内对象**可以通过当前会话撤销；已保存对象采用回收区恢复。界面明确说明两者不同，不假称 Ctrl+Z 可以恢复已经从磁盘安全删除的文件。
- **依赖公共库：**删除项目草稿不能删除或改写公共库原件；删除场景不能删除项目其他场景、已生成的独立 FBX、历史冻结输出。
- **底层事务：**在 `workshop-store.cjs` 的现有版本哈希、路径安全、journal、故障恢复体系上新增支持**move-to-trash/remove intent** 的原子操作；禁止只修改索引却留下孤儿内容、也禁止先 `fs.rm -r` 再更新索引。测试同时模拟中断、外部文件改动、目录符号链接、改名冲突、已占用文件、重复点击、撤销和恢复后再次保存。

### A3／最近项目：打开工坊不再每次选文件夹

- 主页面显示最近打开项目列表（默认最多 12 项）；可一键打开，显示项目名称/目录、最后成功打开时间；缺失项目只标红并提供定位/从历史移除。
- 最近历史存在 Electron `app.getPath('userData')` 下，**不要把绝对路径写进 GitHub、项目公开样例、导出FBX或原生资产文件**；固定结构、容量上限和损坏恢复；禁止任意相对路径注入。
- 可选「启动时恢复上次成功项目」，推荐默认显示最近项目并突出「继续上次」而不是自动打开可疑目录。开启自动恢复必须在项目有效、无冲突且用户已选择后记住偏好。
- 不记录打开失败的路径为成功；打开另一个项目须处理现有未保存数据，选择「保存 / 放弃 / 取消」，取消后保留当前工程。

### A4／卡片与列表的基本可用性

- 资产主视图支持缩略图、名称、源文件类型、修改时间/版本、体素数量、未保存状态；固定按钮最多两个主操作，其余归「⋯」。
- 未生成缩略图时显示清楚的示意占位，**绝不把占位当真实预览**；可先按模块缓存捕获真实预览；阶段 B 再标准化永久缓存。
- 支持列表/卡片切换、模糊搜索、名称排序、类型筛选和场景列表清晰选择态；少量资产时布局居左且内容面积合理，不要一排无限拉长六个卡片。
- 空项目第一屏直接提示「创建第一个资产」或「打开最近项目」，空试摆提示「选择资产后放入预览」。
- **A 包独立验收门槛：**用户能在不到两分钟内完成「打开最近项目 → 新建草稿 → 改名 → 保存 → 删除 → 恢复 → 删除场景 → 重开验证」；不要求先了解发布/公共库/Scene ID。

## 4. B 包：从场景私有源转为项目一级资产（P1，模型迁移）

### B0／模型设计必须先有明确契约

不要在原 `xinghai-workshop-project-1` 下偷偷增加未经校验的可选字段；设计版本化兼容（候选 `xinghai-workshop-project-2` 和相应 Scene v2），或证明更小的迁移方案后在计划日志给出变更理由。字段命名由 Codex 在设计文档提出，但必须包含稳定身份、相对路径、版本、原生类型、预览引用与项目资产表；Scene 只持有引用。

**推荐新项目磁盘布局（供实现时审查，不是未经验证的最终契约）：**

```text
我的工坊项目/
  project.xhproject.json
  assets/
    <assetId>/asset.xhmodule.json           # 工坊可编辑原生体素源
    <assetId>/preview.png                  # 规范化缩略图（可重建）
  scenes/
    <sceneId>/scene.xhscene.json           # 引用 project.assets 中的 assetId
    <sceneId>/preview.png                  # 试摆快照缩略图（可重建）
  .workshop-trash/                        # 回收区，受路径限制、索引及原子事务管理
  .workshop-txn/                          # 现有中断恢复机制
```

源文件**不因更改显示名而改物理路径**。目录统一由项目根管理，用户可以选择项目保存目录、项目内分类文件夹与「另存为新项目」位置，不能让同一个项目的资产直接引用任意外部绝对文件路径以致移动项目时失效。

### B1／独立资产保存与「另存为新资产」

- 资产在**项目级**创建、打开、编辑、保存；不必先创建场景。
- 「保存」更新同一个 assetId/revision；「另存为新资产」显式产生新 assetId，保留旧源，不自动把旧场景实例改指新源。
- 模块编辑页面提供清楚的「保存资产」「另存为新资产」「导出 FBX」；名称修改与保存归属不再依附特定场景。
- 资产保存位置的“文件夹选择”限定在项目受控资产目录，若用户选择其他目录则通过「复制至新项目/导出原生工程」实现，不引入跨项目可变绝对路径。

### B2／实时引用、试摆同步与明确独立化

- 试摆场景的同一 assetId 可以多次摆放；实例只保存 assetId、位置/旋转/分组，不复制整个资产源。
- **修改并保存源资产后**，当前所有试摆场景引用它的实例重新载入新版本视觉，同时保留位置、旋转和实例 ID。若当前编辑器处于未保存状态，可在活动预览中显示「未保存预览」但绝不把脏数据当已提交版本。
- 某个实例需要独立编辑时提供「将此实例另存为独立资产」，即新建资产＋该实例改指作为一个跨文档事务；其他实例与原资产保持不变。
- 从外部公共库引入时，用户明确选择「复制为当前项目资产」；只复制一次，之后同项目的每次摆放共享该**项目副本**。外部库后续修改不应自动改这个本地项目，除非有显式同步流程（本轮不做）。
- Root 移动等会影响所有实例世界位置的操作必须复用现有联合变换/撤销纪律，不能直接挪模型造成全部试摆位置改变。

### B3／预览缩略图与库浏览

- 保存原生资产时生成一张**统一正交或固定斜俯视**的离线模型缩略图：透明或中性背景、固定镜头、稳定光照与包围盒适配；人工可选择自定义预览角度但不改变源几何。
- 缩略图是可重建缓存，用源 assetId/revision/hash 失效；过期不显示错误历史缩略图；项目重新打开后仍可看到图卡。
- 试摆场景保存时生成场景预览图；大场景失败时保留源且给出「预览生成失败」警告，不阻断保存。
- 图片数据尺寸限制与数量预算，避免1000件资产时启动阻塞。初屏只加载可见项目及可见缩略图，测试大型列表滚动。

### B4／旧格式安全迁移

- `xinghai-workshop-project-1` 的旧用户项目保持可读，**默认「备份并转换副本」到用户指定新目录**；不覆盖旧项目。
- 为每个旧私有 voxel Asset 生成一个项目资产登记并保持溯源；改写旧 `SceneDocument.assets` 与 `instances` 的引用到新 ID；全部场景通过引用完整性检查后才将副本标记可用。
- 旧场景不同源即使显示名相同也不能静默合并；若两个旧资产 ID 碰撞但字节/修订不同，则分配新的唯一 ID 并在迁移报告中显式列出映射。
- 旧 `releases/`、发布快照、`GLB/FBX` 成品、Unity 接收数据全部原样保留，不作为新试摆功能的主动编辑对象。
- 支持迁移中断、取消、磁盘不足、部分坏源、只读目录、路径冲突。失败时旧项目及已有新项目副本均可恢复，不能留下半迁移状态冒称完成。

## 5. C 包：围绕独立 FBX 的制作闭环（P1）

### C1／把「导出 FBX」移到模块编辑器主操作

- 模块编辑器主工具条直接提供「导出 FBX…」，导出弹窗只要求**目标文件夹 + 文件名**，高级部分显示 Root/单位/材质摘要和需附带文件。
- 保留内部的 GLB 构造与 Blender 转换能力作为**实现细节**；用户不再被要求先创建发布版本、先进入发布页、选择场景或选择 GLB/FBX 菜单。
- 复用现有经验证的 `blender-fbx-5.1.2` 配方、`glb_to_fbx.py`、材质 `.xhmaterials.json` 和必要 `.xhtextures` 目录；不能为了“只有FBX”而默默丢掉色彩/贴图。若 Blender 未配置或版本不满足要求，给出定位/选择程序及错误说明，不假装直接原生生成 FBX。
- 输出为 `名称.fbx`＋其**实际必要**的旁车/贴图，不再夹带整场景发布结构或公开工坊源文件。对纯颜色/贴图分别记录输出契约，不靠碰运气的材质自动识别。
- 导出操作独立于原生「保存」：提示未保存草稿时可选「先保存并导出 / 仅导出当前已保存版 / 取消」，每个选择明确来源 revision/hash；之前导出的 FBX 保持不变，源更新不会静默覆写外部文件。
- 同名文件已存在时明确「取消 / 另存新名 / 覆盖（可恢复备份）」；默认不覆盖；失败后不留下被误认为成功的半套 FBX。
- 导出后给出路径、打开文件夹、文件有效性、颜色和依赖摘要；至少一次实际 Blender 重导入核验外形/缩放/Root/颜色。Unity 最小导入仅在这次触碰适配器的情况下补做；不修改游戏本体。

### C2／场景装配真正降为试摆预览

- 主导航改名为「试摆场景」。页面顶部显示「这是用于比较比例和组合的草稿，不会对外发布」。
- 保留相机、放置、选择/移动/旋转、批量操作、复制实例、隐藏组、撤销/重做和保存场景草稿。
- 素材浏览优先显示**当前项目一级资产**，不再把「公共库导入独立副本」做为每次放置的唯一途径。
- 场景文件只保存资产 ID 引用和 Transform/分组，不复制/烘焙 FBX；源资产修正后已部署的实例会同步显示修改。
- 场景的「另存为场景」复制组合与实例 IDs，仍引用同项目的资产，不复制整套 asset 文件。用户另需真正独立资产时在资产层操作。
- 场景改名、删除、重开、搜索、预览图在项目页即可完成；不要求进入装配页再找管理入口。

### C3／收起「发布」并保护旧成果

- **新项目模式**隐藏/移除顶部「发布」工作区的普通入口，以编辑器的「导出 FBX」取代；不再提供「发布整个场景」。
- 旧项目兼容入口仅作「查看历史/迁移或需要时打开旧发布」：不删除已有 `core/publish.ts`、Unity `AssetBaker/SceneBaker` 或历史 `releases`。是否未来物理删除这些模块，需单独重构任务，**不在本轮隐式执行**。
- 新 UI 文案、README 和帮助统一使用「保存原生资产」「导出 FBX」「保存试摆场景」三个动作，不再混淆“发布”“保存”“登记公共库”。

### 7.1 最小真实验收剧本（必须用 Electron 做，不可只调用核心函数）

1. 首次打开：看到最近项目和「新建资产」，无需先造一个场景。
2. 新建空模型：自动可识别名称，能立即编辑；不填 Task ID 或长字段。
3. 改名：项目页右键/菜单更名，模块页同步；场景在列表改名，重新启动保持一致。
4. 删除未保存空资产：卡片消失，无孤立文件；关闭重开仍不会复现。
5. 删除已保存无引用资产：移入回收区、正常列表消失；恢复后可继续编辑，同原件字节一致。
6. 删除一个有 3 个试摆实例的资产：提示「被3个实例引用」，不能无提示损坏场景；明确依赖处理后才可删除。
7. 删除一个有实例、私有源和历史发布的旧场景：场景从正常列表消失；其旧发布和公共库原件不被删；恢复后引用完整。
8. 当前项目改名、最近历史一键重开、外部目录移走后的缺失状态，以及未保存时切项目的「保存/放弃/取消」。
9. 资产保存：同一项目 `assets` 生成一个源文件；另存新资产后原资产仍不变，两个ID不同。
10. 缩略图：同一资产固定视角预览，保存后重开仍出现；旧缩略图在源编辑后不继续伪装最新。
11. 试摆：在场景放 10 个同源石柱，场景引用仅一份项目源；编辑并保存石柱后10个同时更新，位置不变。
12. 独立化：将其中 1 个实例另存独立源，再改它，另外9个仍用原版。
13. 两个场景引用同一源：修改此资产，两个场景预览刷新；删除任一场景并不删除资产。
14. FBX：未保存提醒、选目录与名字、成功导出并重导入；修改原生草稿后先前导出的FBX SHA不变。
15. 材质：颜色、透明/贴图、Root、世界单位符合既有验证配方，必要旁车及贴图目录齐全；无 Blender 时给明确错误，不把GLB谎称FBX。
16. 旧v1项目：只读打开、在新目录执行迁移，迁移失败后原工程及已发布记录SHA不变，迁移成功后显示新的项目资产库。
17. 边界：两次点击删除、外部文件变更、只读目录、软链接、进程中断、磁盘不足及取消操作不会让项目半删或半迁移。
18. 布局：1920×1080、1440×900、1000×700各打开主要界面，卡片不过分拉伸，按钮、名称、回收入口及最近历史一眼可见。

### 7.2 判定通过时必须分别写明

- **逻辑通过**：底层引用/命令/事务及迁移测试。
- **桌面通过**：真实鼠标键盘、Electron UI 和磁盘实际写入。
- **外部文件通过**：至少一次真实 Blender 输出/再导入、字节SHA及实际依赖检查。
- **用户手感通过**：必须用户明确试玩认可，自动脚本不能代替。
- **未覆盖**：长时高负载、用户全部旧私有项目、团结运行时验收及后续更复杂地形/建模操作，本轮不假称完成。

## 8. 本轮禁止事项

- 禁止将「删除」实现为仅过滤 UI 列表，磁盘/引用仍留坏数据；也禁止对任意路径直接 `rm -rf`。

- 禁止用显示名称做稳定文件身份，改名不允许造成场景实例引用丢失。
- 禁止借 UX 改版重写/删除原有模块笔刷、体素内核、Undo、Root、材质配方。

- 禁止扫全项目源码、全部用户 Excel、原作游戏资源或其他工坊；只读与本任务有关的真实文件。
- 禁止为满足形式而跑超大验证矩阵；按本任务敏感边界选择性验证。
- 禁止隐瞒本机 HEAD 与远端不同、测试失败或复用旧二进制而未重新打包。

> 随后沿同一批准范围推进 B/C（除非用户在 Gate 调整方向）：工坊资产成为项目级原生源，试摆场景只持有资产引用、编辑源后同步更新；以**单独资产 FBX 导出**为主要外部出口，旧 GLB/发布历史和 Unity 代码保留兼容，不再让新用户发布整张场景。真正碰到需要用户决定的数据破坏风险时，记录具体方案才停下；其余正常技术实现自行完成。
>
> 保护 `asset_workshop_2d`、用户维护区、开发细则、游戏本体、原作资源及所有其他并行修改。原型按 §7.1.1 A 级为主，破坏性删除/迁移/存储边界做定向 B 级测试。每个包结束后核对并选择性提交/推送 GitHub `main`（不得强推/Gitee），列出实现、技术验证、用户未验收和剩余阻塞。不要把聊天中输出的计划称为已写入仓库。

**计划结论：**最急迫的不是增加新建模功能，而是让用户能够**创建、命名、找到、保存、删除、恢复、继续编辑**；在此基础上从「场景驱动」迁到「原生资产驱动」，再把对外交付收敛为独立 FBX。做对这条主线以后，体素建模和试摆才不会被繁琐项目管理拖慢。
